# Serein 调研与实施计划：v2 复审修改建议稿

日期：2026-10-21。审阅对象：[调研与实施计划 v2](emotional-agent-research-and-plan.md)。

此前修改建议已合入主计划 v2。本文件替换原建议稿，现仅记录本轮复审发现的 6 项待完善内容，供下一次修改主计划时使用；本次不改动主计划。

v2 已收紧首版范围，将微信和主动跟进后移，并分离模型初筛、策略与偏好记忆实验。当前可以启动第一周验证，后续应优先消除数据与准入规则的歧义，不再增加首版功能。以下为建议条文，新增参数均需在实际实施前确定。

## 1. 明确在线数据、备份及恢复的保留期限

对应主计划：第 6.1、6.3 节。

**问题：**原文最多保留 7 天、备份最多保留 7 天，并不自动等于所有副本总共保留 7 天。接近在线到期的原文进入新备份后，物理保留时间可能接近 14 天。恢复流程目前强调删除与授权标记，还应清理自然到期的数据。

建议补入第 6.1 节：

> 分别说明在线数据保留期限、备份从创建起的保留期限及原文在全部副本中的最长保留时间。如果采用在线原文最多 7 天、备份创建后最多 7 天的策略，应说明原文在备份中的总保留时间可能接近 14 天，不将其描述为所有副本仅保存 7 天。最终参数在试用前固定并告知用户。

建议补入第 6.3 节：

> 每项有期限的数据记录原始到期时间。恢复备份后，先隔离恢复环境；在开放访问、启动任务和发送回复前，清理超过原始到期时间的数据，再应用删除、更正及授权变更记录。恢复操作不得重置数据的到期时间。

补充验收：使用可控时钟覆盖“未到期数据进入备份 → 数据自然到期 → 恢复旧备份”，确认过期原文不再参与检索、上下文或后台任务。另行核验物理备份是否在明示期限内清理。

## 2. 区分聊天原文到期与偏好确认凭据到期

对应主计划：第 4.2、6.1、6.2 节。

**问题：**偏好暂定保留到试用结束，而聊天原文最多保留 7 天；同时计划要求删除确认来源时同步删除派生记忆。如果确认来源直接依赖聊天原文，偏好可能随第 7 天的原文清理一起消失。

建议采用最少确认凭据独立保存的方式，补入第 4.2 节：

> 偏好内容与最少确认凭据作为独立的记忆记录保存。确认凭据仅包含用户作用域、被确认的偏好及版本、确认时间和必要操作标识，不复制完整倾诉原文。其期限与偏好一致，不通过保存完整消息延长原文保留时间。

将第 6.2 节有关来源删除的规则细化为：

> 聊天原文按期清理不自动等于撤回已经独立确认的偏好。用户明确撤回偏好、删除该偏好的确认凭据，或删除本方全部对话及记忆时，同步清理相关偏好及派生状态。用户要求删除某段来源内容时，应明确其关联记忆的处理范围，不能留下可恢复该内容的记忆副本。

补充验收：

- 聊天原文到期后，已独立确认且仍有效的偏好按预期保留。
- 撤回偏好或删除全部数据后，记忆及确认凭据均不可再用。
- 更正后仅新版本有效；历史上下文、后台任务和备份恢复不会重新启用旧版本。

如果选择偏好随原文到期的另一方案，应改写偏好保留承诺并测试该行为，避免两套规则同时存在。

## 3. 为评测的通过、失败和证据不足分别规定动作

对应主计划：第 1 节决策表、第 9.2、9.3、10 节。

**问题：**验收允许将对话增益记为“未确定”，但进入试用又要求先完成离线体验验收。需要说明未确定是否允许探索性试用，否则可能不断调提示词而无法进入真实验证。

建议在第 9.3 节增加决策表：

| 结果 | 后续动作 |
| --- | --- |
| 授权、隔离、删除、不保存或关键响应边界测试失败 | 阻止进入试用；修复并回归后重新判断 |
| 关键要求通过，但体验出现事先定义的明显退步 | 先修订策略，或退回已验收的普通人设基线；不以增加功能掩盖退步 |
| 关键要求通过，体验证据不足且未观察到明确退步 | 可以开展原定人数范围内的探索性试用；如实说明尚未证实优于基线，不因此扩大规模或作效果承诺 |
| 关键要求通过，体验达到预先确定的目标且证据支持 | 按计划进入受邀试用，继续观察真实使用情况 |

建议同时补充：

> 在查看正式验收结果前，确定体验退步、证据不足和增益成立的判定规则，以及策略修订的时间预算。预算结束后必须选择继续探索、简化策略、更换方向或停止，不默认无限增加迭代轮次。修订后保留回归检查，不通过反复挑选同一验收集的最好结果宣称增益。

小范围探索性试用仍需满足其余工程、数据和费用准入条件。该分支仅区分体验证据强弱，不降低关键要求。

## 4. 补充自然语言控制的误触发边界

对应主计划：第 6.2、7.2、9.2 节。

**问题：**“对象不清时澄清”不能覆盖引用、否定、假设和转述。例如“别删除我的记录”对象明确，但不是删除授权。

建议补入第 6.2 节：

> 执行控制操作前，确认当前用户是在对本服务发出操作指令。引用、转述、否定、假设及对功能的询问不直接触发操作。固定命令或按钮走确定路径，明确区分取消确认与执行确认；自然语言存在歧义时先澄清，不因出现控制关键词而执行。

> “开启不保存”“停止当前回复”等固定控制入口由本地逻辑处理，不依赖付费模型。在自然语言控制识别能力受限时，明确提供可用的固定入口，不声称所有表达都能自动执行。

补充固定测试：

| 输入或操作 | 预期 |
| --- | --- |
| “他让我删除全部记录” | 不执行删除 |
| “别删除我的记录” | 不执行删除 |
| “如果我说删除全部记录会怎样？” | 解释功能，不执行删除 |
| 在引用内容中出现“开启不保存”或“停止回复” | 不仅因引用内容触发模式切换或取消 |
| 当前用户通过固定入口明确要求删除全部记录 | 按定义执行并报告真实结果 |
| 重复提交同一已执行的控制请求 | 不产生相互矛盾的状态，不把失败显示为成功 |

自然语言澄清与固定入口的执行语义保持一致，相关状态变化纳入在途任务和恢复测试。

## 5. 将人工评测的人力纳入排期

对应主计划：第 9.1、10 节。

**问题：**60–100 个多轮脚本、两组对比及关键样本双人复核已有方法说明，但尚未落实评审人及所需时间。

建议在第 9.1 节区分三类样本：

- 对话体验脚本：人工盲评，报告独立场景及评分结果。
- 记忆、控制和工程脚本：优先使用可确定结果的自动校验，不全部计入体验胜率分母。
- 关键响应边界样本：人工复核，单列结果；与体验集重合时说明，不重复当作独立证据。

建议在第 10 节增加评测资源表，正式验收前填写：

| 项目 | 需确定的内容 |
| --- | --- |
| 体验盲评 | 参与评审的人、独立脚本数、B 对 A 与 C 对 B 的覆盖范围 |
| 关键复核 | 需双人复核的样本、第二位评审是否可用、分歧处理人 |
| 时间预算 | 生成与整理、实际阅读评分、分歧处理及回归各占多少时间 |
| 资源不足处理 | 调整样本量或顺延日期，并如实降低结论强度；关键要求不能因人手不足略过 |

工作量示例仅用于估算：80 个脚本 × 2 组配对比较 × 2 位评审 × 每次 3 分钟，约为 16 小时，尚未包含准备和分歧处理。实际仅部分样本双评时，应按实际数量重算，不能把该示例当作固定承诺。

## 6. 第一周增加一个最小贯通样例

对应主计划：第 2.2、10 节。

**问题：**第一周偏重访谈、选型和基线，保存模式及优先控制等架构约束集中在第二周，可能较晚才发现适配器或队列不支持核心要求。

建议将第 1 周退出条件补充为：

> 在同一最小样例中完成授权用户的一次收发、未授权请求拦截、一条不保存消息不进入本方持久存储，以及生成过程中停止后旧结果不再开始交给渠道。样例纳入已有渠道及集成实验预算；采用合成输入，不等待真实倾诉数据。

第 1 周样例只验证关键路径与适配能力，不要求完成全部控制界面、备份治理和正式验收。第 2 周扩展为完整能力，第 3 周完成回归及首次试用准入。

建议明确四项样例证据：

- 授权用户的收发及投递状态可查。
- 未授权用户的输入不进入模型或内容存储。
- 不保存样例的原文不出现在本方任务表、数据库和受控日志中。
- 停止请求在生成期间使旧任务失效；发送交接前检查失败后丢弃结果。

若适配框架无法满足样例，按限时实验规则记录阻塞并选择直连或调整路径，不继续在其上叠加记忆功能。预算超出时更新日期，不压缩后续验收。

## 修改顺序与保留项

优先将第 1–4 项写入主计划对应规则，第 5–6 项落实到任务表、负责人和退出条件。原有 Python、SQLite、模块化单体、单渠道及最小偏好记忆范围继续保留；无需为本轮修改引入额外框架或扩大首版功能。
